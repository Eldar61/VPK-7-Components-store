# Подробный план двух микросервисов ВПК-7

## 1. Архитектура и границы ответственности

Сохраняем выбранную схему: **два сайта, два самостоятельных API и две отдельные базы данных**. Оба backend разрабатываются на C# / ASP.NET Core (.NET 10), оба frontend — на React + TypeScript + Vite. Для графиков на сайтах использовать Recharts: он поддерживает круговые, столбчатые и линейные диаграммы. [Поддержка .NET](https://dotnet.microsoft.com/en-us/platform/support/policy/dotnet-core), [Vite](https://vite.dev/guide/), [Recharts](https://recharts.github.io/en-US/api/).

- **Сервис Эльдара** владеет пользователями своего сайта, черновиками и сохранёнными конфигурациями, правилами технической совместимости, расчётом мощности и статистикой цен сборок.
- **Магазин Семёна** владеет каталогом и характеристиками товаров, ценами, остатками, скидками, корзинами, резервами, подтверждёнными покупками и статистикой продаж.
- Сервисы общаются только через REST/JSON и не читают базы друг друга. Магазин передаёт набор деталей в чистый метод проверки совместимости сборщика; этот метод не вызывает магазин обратно.
- У сайтов раздельные аккаунты. Из сайта сборки заказ поступает в магазин как внешняя гостевая корзина. Учебное подтверждение покупки не включает настоящую оплату и доставку.

В частности, удалить вторую *магазинную* корзину из модели сборщика и перенести запись продажи с момента резервирования на момент подтверждения. :codex-file-citation{path="D:\Институт\4 курс\ВПК_7\VPK-7 Проект\Информация о микросервисах\Информация микросервиса (Сервис сборки ПК) Дубовский Эльдар\Практическая работа №2.docx" purpose="source"} :codex-file-citation{path="D:\Институт\4 курс\ВПК_7\VPK-7 Проект\Информация о микросервисах\Информация микросервиса (Магазин комплектующих) Абрамов Семён\ВПК-7_ПР_№2.docx" purpose="source"}

## 2. Эльдар: алгоритм сборки и исправление UML

### Activity UML — порядок действий

Разделить диаграмму на дорожки **«Покупатель» → «Сайт сборки» → «API сборки» → «API магазина»**. Показать следующий цикл:

1. Покупатель входит в аккаунт, создаёт черновик, задаёт бюджет и выбирает детали. API сборки сохраняет ID деталей и количества.
2. API сборки запрашивает у магазина выбранные товары **вместе с характеристиками**. Если магазин недоступен, черновик сохраняется, пользователь видит ошибку связи и может повторить запрос. Состояние «технически несовместима» здесь не устанавливается.
3. Сборщик проверяет полноту и корректность данных, выполняет технические проверки из раздела 3 и рассчитывает мощности.
4. При технических ошибках сайт показывает каждую причину. По запросу пользователя сборщик получает у магазина доступные замены, подставляет кандидатов **по одному**, повторно проверяет всю сборку и предлагает только прошедшие проверку варианты. Выбор замены возвращает процесс к редактированию черновика.
5. Для технически допустимой сборки сборщик запрашивает у магазина предложение с актуальными ценами, скидками и наличием. Бюджет и наличие оцениваются **отдельно** от совместимости. При нехватке товара или превышении бюджета пользователь может изменить черновик и повторить проверку.
6. Сайт показывает итог проверки, предварительную цену и круговую диаграмму мощности. Пользователь сохраняет полную проверенную сборку; сохранённая версия становится неизменяемой. Для изменения создаётся новый черновик на её основе.
7. По желанию покупатель передаёт состав сборки в магазинную корзину. Магазин возвращает `cartId`, затем по отдельному действию покупателя повторно проверяет цену и остатки и создаёт резерв.
8. Покупатель подтверждает учебную покупку или отменяет резерв. Сайт сборки показывает состояние, полученное из магазина.

На новой Activity-диаграмме ветви ошибки должны возвращаться к редактированию или повтору запроса. **Конечный узел ставится только после действительного завершения сценария**; на нынешней схеме после некоторых конечных узлов действия продолжаются. Сохранение сборки не следует делать обязательным следствием успешного резервирования. :codex-file-citation{path="D:\Институт\4 курс\ВПК_7\VPK-7 Проект\Информация о микросервисах\Информация микросервиса (Сервис сборки ПК) Дубовский Эльдар\Практическая работа №2.docx" purpose="source"}

### Sequence UML — сообщения между участниками

Показать участников `Buyer`, `AssemblyUI`, `ConfigurationController`, `ConfigurationService`, `AssemblyDb`, `ShopClient`, `ShopApi`, `CompatibilityChecker`, `PowerCalculator`, `RecommendationService`. Временной порядок сообщений: создать черновик в БД → запросить характеристики через `ShopClient` → проверить состав и совместимость → рассчитать мощности → при успехе запросить предложение магазина → сравнить с бюджетом → вернуть результат интерфейсу → сохранить снимок конфигурации → создать магазинную корзину → резервировать → подтвердить или отменить.

Использовать блоки UML `alt` для несовместимости, отсутствия товара, превышения бюджета, истёкшего предложения и недоступности магазина; `loop` — для изменения деталей и повторной проверки; `opt` — для рекомендаций и оформления покупки. `ConfigurationService` управляет сценарием, а объект `PCConfiguration` хранит состояние: HTTP-вызовы не должны исходить непосредственно из сущности. **Не запускать техническую проверку параллельно с первоначальным получением характеристик**: ей требуются эти данные.

В диаграмме состояний разделить два жизненных цикла: конфигурация (`DRAFT → CHECKING → VALID/INVALID → SAVED`) принадлежит сборщику; корзина и резерв (`DRAFT → RESERVED → CONFIRMED/CANCELLED/EXPIRED`) принадлежат магазину. Сбой магазина не переводит конфигурацию в `INVALID`.

## 3. Эльдар: правила проверки и новые графики

**Вход проверки:** ID и количество выбранных деталей. Магазин возвращает типизированные характеристики. Для полной сборки обязательны CPU, материнская плата, RAM, GPU, БП, корпус и хотя бы один накопитель. CPU, плата, GPU, БП и корпус выбираются по одному; RAM и накопителей может быть несколько. Количество каждой позиции положительное.

Проверки выполняются в следующем порядке:

1. Все ID существуют, товары активны, фактические категории совпадают с выбранными; обязательные характеристики заполнены.
2. Сокет CPU равен сокету платы.
3. Тип RAM совпадает с поддерживаемым платой; количество модулей не превышает число слотов; суммарная ёмкость не превышает предел платы.
4. На плате есть слот для GPU; длина GPU не превышает предел корпуса; число требуемых разъёмов питания GPU не превышает число подходящих разъёмов БП. Различие поколений PCIe само по себе не является ошибкой.
5. Форм-фактор платы и БП поддерживается корпусом; для накопителей хватает подходящих портов платы и мест в корпусе.
6. Для каждого потребителя мощности каталог содержит **оценочную мощность в ваттах**. `totalPowerW = Σ(quantity × estimatedPowerW)` для CPU, платы, RAM, GPU, накопителей и вентиляторов корпуса. `requiredPsuW = ceil(totalPowerW × 1,25)`; мощность выбранного БП должна быть не ниже этого значения. БП в сумму потребителей не включается.

API возвращает код и описание каждой ошибки с ID затронутых деталей. Отдельные поля `compatible`, `available` и `withinBudget` не позволяют смешать техническую проблему, остаток и цену. Если данных для правила не хватает, возвращается ошибка «характеристика отсутствует», а не положительный результат по умолчанию.

**Круговая диаграмма:** на экране результата проверки показывать расчётную *потребляемую мощность*, Вт. Сектор каждой детали равен `quantity × estimatedPowerW`; подпись и подсказка показывают ватты и долю `sectorW / totalPowerW × 100%`. БП не рисовать как потребителя. Нулевые секторы пропускать; если расчёт невозможен, показывать перечень недостающих характеристик вместо диаграммы. Это **оценка по каталогу**, а не измерение электрической энергии.

**Гистограмма цен:** учитывать каждую **сохранённую, полную, успешно проверенную** конфигурацию ровно один раз по цене предложения магазина на момент сохранения. Черновики, повторные проверки и покупки не добавляют новые наблюдения. Сохранённый снимок цены не меняется вслед за будущими ценами магазина. Для суммы `priceRub ≥ 0` диапазон начинается с `floor(priceRub / 50 000) × 50 000` и заканчивается перед следующей границей. API возвращает диапазоны по возрастанию, включая пустые промежуточные интервалы; сайт показывает по оси **X — диапазоны в ₽**, по оси **Y — число конфигураций**. Гистограмма доступна всем, отдаёт только агрегаты без данных пользователей. Если сохранённых сборок нет, показывать пустое состояние.

## 4. Семён: алгоритмы магазина и статистика администратора

- **Каталог:** администратор создаёт и изменяет товары, характеристики, цену, количество и акции. Некорректные или отрицательные значения отклоняются. Товар с историей покупок архивируется, а не физически удаляется: снимки прошлых продаж сохраняются.
- **Расчёт цены:** для каждой позиции определить действующие акцию, скидку за количество и скидку по типу покупателя; применить **одну наибольшую**. Первичные учебные значения: `STANDARD — 0%`, `REGULAR — 5%`, `WHOLESALE — 10%`; за количество `2–4 — 3%`, `5+ — 7%`. Тип новому покупателю назначается `STANDARD`, иной тип меняет администратор; внешней гостевой корзине всегда назначается `STANDARD`. Процент акции задаёт администратор. Стоимость позиции — цена × количество × `(1 − скидка/100)` с округлением до копеек, итог — сумма позиций. Реальная доставка в этой версии отсутствует.
- **Предложение и резерв:** предложение действует 15 минут и ничего не меняет на складе. Доступное количество равно физическому остатку минус действующие резервы. При резервировании магазин в одной транзакции повторно проверяет цену и количество и резервирует **все позиции либо ни одной**. Резерв действует 15 минут. Повтор с тем же ключом операции возвращает прежний результат. Отмена или истечение срока освобождает резерв; подтверждение уменьшает физический остаток и создаёт одну запись продажи на позицию.
- **Рекомендации:** для недоступной позиции искать активные товары той же категории с достаточным остатком; сортировать сначала по числу подтверждённо проданных единиц за последние 90 дней, затем по близости цены, затем по ID. Подмена происходит только после выбора покупателя. Для рекомендации целой сборки магазин формирует до трёх доступных вариантов в пределах бюджета и проверяет каждый вызовом чистого API совместимости Эльдара. При недоступности проверки вариант нельзя помечать совместимым.

**Сбор статистики:** источник — только подтверждённые покупки и неизменяемые снимки их позиций (`productId`, категория, количество, цена после скидки, сумма, время подтверждения). Резервы, черновики и отмены до подтверждения исключены. В запросе администратора задаются период `[from, to)`, группировка день/неделя/месяц и необязательная категория. Время хранится в UTC, для отображаемых периодов переводится в `Europe/Moscow`. Для каждой группы рассчитываются количество заказов, сумма проданных единиц и выручка; средний чек — выручка / число заказов. Пустые даты заполняются нулями. Популярность товара — сумма проданных единиц, при равенстве сортировать по выручке и ID. Динамика относительно предыдущего периода той же длины: `(текущий − предыдущий) / предыдущий × 100%`; при нулевом предыдущем значении показывать «нет базы для сравнения».

**Экран администратора:** карточки «заказы», «продано единиц», «выручка», «средний чек»; линейный график выручки по времени; столбчатый график количества продаж по времени; горизонтальная диаграмма пяти самых продаваемых товаров и диаграмма продаж по категориям. Фильтры периода, группировки и категории меняют запрос к API; все суммы и группировки рассчитывает backend, frontend только отображает результат. При отсутствии продаж показывать нули и понятное пустое состояние. ## 5. Контракт, проверка и разработка

Минимальные маршруты сборщика: создание/изменение/проверка/сохранение конфигурации, получение сохранённой конфигурации, `POST /api/compatibility/check` для магазина и `GET /api/statistics/price-buckets`. Магазин предоставляет каталог, расчёт предложения, создание корзины, резервирование, подтверждение и отмену; администратору — управление каталогом и `GET /api/admin/analytics`. Схемы запросов, ответов и ошибок зафиксировать в OpenAPI до реализации двух сайтов.

Проверить тестами каждое правило совместимости и граничную мощность БП; сумму секторов диаграммы; границы гистограммы 49 999,99/50 000 ₽ и однократный учёт сохранённой сборки; применение лучшей скидки; исключение резервов из продаж; суммы, периоды и пустые интервалы статистики; конкурирующее резервирование последней единицы, повтор запроса, истечение предложения, отмену и недоступность партнёра. Затем сверить исправленные Activity, Sequence и state-диаграммы с реально работающими сценариями и выполнить интеграционные запросы к размещённым API.

Разработку можно продолжить в VS Code с [официальным расширением Codex](https://learn.chatgpt.com/docs/codex/ide). Перед началом кода сохранить этот план и согласованные JSON-схемы в репозитории: они станут общей спецификацией для вас, Семёна и дальнейших чатов.
