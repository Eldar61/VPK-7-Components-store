# Магазин комплектующих Семёна Абрамова

Самостоятельный микросервис ВПК-7: каталог реальных комплектующих, собственные аккаунты, учебные покупки, резервы склада и статистика администратора. API совместим с сервисом сборки ПК Эльдара. Сервисы общаются по HTTP/JSON и используют отдельные базы данных.

## Начальный каталог

В data/catalog.json находятся **442 реальных артикула**:
- CPU — 61;
- материнские платы — 55;
- RAM — 62;
- видеокарты — 57;
- блоки питания — 50;
- корпуса — 88;
- накопители — 69.

Отдельными позициями являются реальные варианты поставки с собственным артикулом: ёмкость, мощность, цвет и исполнение. Это не 442 независимых семейства оборудования. Источники и использованные характеристики: data/sources.json; пояснения: docs/CATALOG.md. Производители: AMD, Intel, MSI, Kingston, Corsair, Fractal Design, Samsung. В карточке сайта есть ссылка на источник.

**Цены в ₽ и складские остатки учебные.** Оценочная мощность отдельно подписана: это не измерение из розетки. BIOS, охлаждение CPU, PCIe bandwidth, размеры M.2, разделение линий и толщина GPU не проверяются текущим контрактом сборщика.

## Что установлено и использовано

C# / .NET 10, ASP.NET Core Minimal API, EF Core 10.0.5, Npgsql EF Provider 10.0.1, PostgreSQL 17 в Docker, Swagger / Swashbuckle 10.1.7. React 19, TypeScript 5.9, Vite 7, Recharts 3. npm фиксирует точные версии в frontend/package-lock.json.

## Запуск в VS Code

Откройте эту папку либо PcShop.code-workspace. Нужны .NET SDK 10, Node.js/npm и запущенный Docker Desktop. Команды выполняются из корня **микросервиса магазина**, не из общей папки ВПК-7.

Терминал 1 — БД:
```powershell
docker compose up -d --wait database
```

Терминал 2 — API:
```powershell
dotnet run --project src/PcShop.Api
```

Терминал 3 — сайт:
```powershell
cd frontend
npm.cmd ci
npm.cmd run dev
```

Повторять npm.cmd ci при каждом запуске не нужно. В PowerShell используйте npm.cmd: это не требует разрешать npm.ps1 через ExecutionPolicy.

- Сайт: http://127.0.0.1:5174
- API / Swagger: http://localhost:5081/swagger
- Процесс: http://localhost:5081/health
- Готовность БД: http://localhost:5081/health/ready
- PostgreSQL: localhost:5434, база pc_shop, пользователь shop.
- Локальный пароль БД: local-development-only (либо POSTGRES_PASSWORD из окружения; строку подключения API тогда также нужно обновить).

В Development первая инициализация создаёт схему и добавляет недостающие seed-артикулы. Повторный запуск не сбрасывает остатки, цены и изменения администратора. Товар не удаляется из БД при исключении из seed. EnsureCreated создаёт только новую схему: для будущих изменений существующих таблиц нужны EF-миграции или согласованный SQL.

В ходе разработки штатная PostgreSQL уже создана в Docker-томе pc-shop_shop-data и заполнена каталогом. Отдельные проверки проводились на тестовой PostgreSQL, их фиктивные продажи в штатную БД не перенесены.

## Вход администратора

Только для локального Development:
- логин: **admin**
- пароль: **Shop-local-admin-2026!**

Обычный покупатель регистрируется на сайте и получает STANDARD. Администратор меняет тип на REGULAR или WHOLESALE во вкладке «Покупатели». Назначение роли ADMIN через публичную регистрацию невозможно.

В Production задайте Bootstrap__AdminLogin и Bootstrap__AdminPassword до первой инициализации. Эти переменные создают первого администратора, а не меняют пароль уже существующего аккаунта. Пользовательские сессии — случайные Bearer-токены на 12 часов, их SHA-256 хранится в БД; это не JWT. Пароли хеширует ASP.NET PasswordHasher.

## Связь с сервисом Эльдара

1. **Остановите tools/ShopStub** сборщика: настоящий магазин занимает тот же порт 5081.
2. Запустите магазин по инструкции выше.
3. В отдельном терминале из папки сборщика запустите его собственную БД и API на 5080.
4. У магазина Assembly:BaseUrl по умолчанию http://localhost:5080/.
5. У сборщика Shop:BaseUrl по умолчанию http://localhost:5081/.
6. В Development оба используют учебный ключ development-only-service-key.

Исходники сборщика менять не потребовалось. Магазин отдаёт тот же Product/Quote/ShopCart JSON. Пример полной проверенной конфигурации с реальными ID — docs/example-build.json. Он прошёл чистый API совместимости Эльдара.

Когда сервисы будут на разных ПК или в облаке, замените адреса на доступные сетевые URL и задайте одинаковый случайный Integration__ServiceKey на обоих backend. В frontend этот ключ не передаётся. Межсервисное общение не зависит от браузерного CORS.

## Правила магазина

**Скидки.** Для каждой позиции применяется максимум из действующей акции, количества (2–4: 3%; 5+: 7%) и типа покупателя (STANDARD 0%, REGULAR 5%, WHOLESALE 10%). Внешняя корзина сборщика всегда STANDARD. Округляется вся строка до копеек, midpoint away from zero. Скидки не складываются.

**Предложение.** Действует 15 минут и не изменяет склад. Перед резервом повторно проверяются каждая цена, скидка, состав и доступное количество. При изменении нужен новый Quote и отдельное действие покупателя.

**Резерв.** Действует 15 минут; физический остаток ещё не уменьшается. Доступно = физический остаток − неистёкшие RESERVED. Все изменения склада, резервов, типов покупателей и карточек сериализованы транзакцией PostgreSQL с pg_advisory_xact_lock. Поэтому несколько процессов API не резервируют последнюю единицу одновременно. Это простая учебная блокировка всего магазина, не оптимизация для большого трафика.

**Покупка.** Confirm уменьшает физический остаток и создаёт одну SaleLine на позицию. Цены/имена/категории берутся из снимка резерва. Отмена и истечение резерва продажу не создают. Повтор с тем же ключом возвращает сохранённый ответ; изменённый запрос с тем же ключом отклоняется. После тайм-аута сначала обновляйте состояние. Успешно подтверждённую покупку нельзя отменить этим сценарием; возвраты не входят в текущую версию.

**Каталог.** Все административные изменения проверяются на сервере; Version защищает от перезаписи устаревшей карточкой. Остаток нельзя сделать меньше действующих резервов. Удаление реализовано архивированием, история продаж сохраняется.

**Рекомендации.** Альтернативы товара: та же категория, достаточный остаток; затем продажи за 90 дней, близость цены и ID. Полный комплект: ограниченный перебор доступных компонентов, бюджет и обязательный вызов чистого API сборщика; до трёх результатов. Это не поиск глобально оптимальной сборки. При недоступном сборщике возвращается 503, совместимость не выдумывается.

## Аналитика

Вкладка администратора «Статистика магазина»: заказы, единицы, выручка, средний чек; выручка и количество по времени, топ-5 товаров, категории. Есть период [from,to), день/неделя/месяц и категория. Начало недели — понедельник. Хранение времени UTC, границы календарных групп — Europe/Moscow. Пустые интервалы заполняются нулями.

Источник — только неизменяемые подтверждённые SaleLine. Заказ считается DISTINCT по OrderId. При фильтре категории чек и выручка относятся только к её позициям, а число заказов — к заказам, где они были. Динамика сравнивает с предыдущим периодом той же абсолютной длины; при нулевой базе null. Сервер рассчитывает все агрегаты, frontend только рисует.

Статистика изначально пустая: искусственные продажи для красивых графиков не добавляются. Создайте и подтвердите учебную покупку через сайт, чтобы появились наблюдения.

## Проверка изменений

```powershell
dotnet build PcShop.slnx
dotnet run --project tests/PcShop.Tests
cd frontend
npm.cmd run build
```

Тесты Domain — консольный проект, запускать через dotnet run, не dotnet test.

HTTP-проверка создаёт собственные тестовые аккаунты/товары/покупки. Направляйте API в отдельную тестовую БД. При работающем таком API:
```powershell
node scripts/integration.mjs
```
При работающем сборщике установите TEST_ASSEMBLY=1. SECOND_SHOP_URL позволяет направить конкурентный резерв во второй экземпляр API с той же тестовой БД. Для SQL-фикстур истечения задайте SHOP_TEST_DB_CONNECTION (libpq connection string) и при необходимости PSQL_PATH. Они меняют сроки только созданных этим тестом корзин.

Готовые ручные запросы: requests.http (REST Client) и docs/postman_collection.json (Postman). Протокол фактических проверок: docs/VERIFICATION.md.

## Остановка

Ctrl+C в терминалах сайта и API. Из корня магазина:
```powershell
docker compose stop
```
Это сохраняет каталог и покупки. Не удаляйте Docker volume ради обычной остановки.

## Облако

Dockerfile API готов к Render/аналогичному Docker-хостингу. Контекст сборки — корень микросервиса; Dockerfile src/PcShop.Api/Dockerfile; порт 8080. В Production обязательны:
```text
ConnectionStrings__ShopDb=Host=...;Port=5432;Database=...;Username=...;Password=...;SSL Mode=Require
Integration__ServiceKey=<случайный общий секрет от 20 символов, не development...>
Assembly__BaseUrl=https://<api-сборщика>/
AllowedOrigins__0=https://<сайт-магазина>
Database__Initialize=true
Bootstrap__AdminLogin=<логин>
Bootstrap__AdminPassword=<пароль от 12 символов>
```
Database__Initialize=true использовать для первоначальной схемы; затем управлять её изменениями отдельно. Frontend публикуется как статический сайт из frontend/dist; VITE_API_URL задаётся при сборке. Реальная публикация в облаке в эту работу не входила. Локальные пароли не переносите как реальные production-секреты.
