# Сервис сборки ПК

Микросервис Дубовского Эльдара для дисциплины ВПК-7. ASP.NET Core (.NET 10), PostgreSQL, React + TypeScript + Vite, Recharts. Сервис создаёт и проверяет конфигурации ПК, показывает распределение расчётной мощности, сохраняет неизменяемые сборки и строит гистограмму их цен с шагом 50 000 ₽.

## Запуск в VS Code

Откройте **эту папку** через «Файл → Открыть папку» или файл `PcAssembly.code-workspace`. После установки Node.js перезапустите VS Code, чтобы его терминал получил обновлённый PATH. Установлены C# Dev Kit, C#, .NET Install Tool, ESLint и REST Client; Codex был установлен ранее.

Нужны .NET SDK 10, Node.js LTS с npm и запущенный Docker Desktop. В отдельных терминалах VS Code выполните:

```powershell
# 1. В корне проекта — PostgreSQL с отдельным постоянным томом
docker compose up -d --wait database

# 2. В корне — временный HTTP-стенд магазина
dotnet run --project tools/ShopStub

# 3. В корне — API сборки
dotnet run --project src/PcAssembly.Api

# 4. В новом терминале — сайт
cd frontend
npm ci
npm run dev
```

Сайт: http://127.0.0.1:5173. Swagger: http://localhost:5080/swagger. API: http://localhost:5080. Тестовый магазин: http://localhost:5081. Зарегистрируйте аккаунт на сайте; пароль — от 10 символов. Готовых пользовательских аккаунтов в исходниках нет.

Для совместимой демонстрационной сборки выберите CPU A6, B650, два модуля DDR5, GPU G8, БП 650 Вт, корпус Air и SSD M.2. Расчёт: **307 Вт**, требуемый БП с запасом 25% — **384 Вт**. Цена с учебной скидкой за два модуля RAM — 97 700 ₽. Детали каталога стенда — условные учебные модели, их мощности не являются спецификациями реального оборудования.

## Что реализовано

- Отдельные аккаунты: регистрация, вход, выход; пароли хешируются ASP.NET PasswordHasher, в БД хранится только хеш токена сессии (срок 12 часов). Доступ к конфигурации проверяется по владельцу.
- Черновики с проверкой версии при изменении; характеристики загружаются по HTTP **до** технической проверки. Ошибка магазина возвращает 503 и не делает сборку технически несовместимой.
- Проверки существования, активности, категории и количества деталей, сокетов, RAM, слота и размеров GPU, разъёмов питания, форм-факторов платы/БП/корпуса, портов и мест накопителей. Нехватка характеристик — явная ошибка.
- Расчёт `Σ(quantity × estimatedPowerW)`, круговая диаграмма по потребителям, БП исключён из секторов. Минимум БП: `ceil(totalPowerW × 1.25)`. Наличие и бюджет отделены от совместимости.
- Сохранение только проверенной полной сборки с неистёкшим предложением. Повторное сохранение не дублирует статистику. Цена и характеристики заморожены; изменение — через копию в новый черновик. Сохранить технически корректный вариант можно и при превышении бюджета или временном отсутствии товара: эти признаки не меняют его совместимость.
- Поиск до трёх замен одной детали с повторной проверкой всей сборки, цены и наличия. Если требуется заменить несколько деталей одновременно, алгоритм не обещает найти решение.
- Публичная обезличенная гистограмма цен с пустыми промежуточными интервалами. Черновики и проверки без сохранения не учитываются.
- Передача в магазинную корзину и проксирование обновления предложения, резервирования, подтверждения, отмены и получения состояния. API сборки хранит только ссылку на корзину и ключ импорта; склад и продажи остаются у магазина.

## Структура и проверки

`src/PcAssembly.Domain` — чистые правила и DTO; `src/PcAssembly.Api` — HTTP, пользователи, PostgreSQL и оркестрация; `frontend` — интерфейс; `tools/ShopStub` — отдельный тестовый HTTP-сервер; `tests` — исполняемые тесты правил без внешнего тестового фреймворка; `docs` — контракт и исправленная UML-логика.

```powershell
dotnet build PcAssembly.slnx
dotnet run --project tests/PcAssembly.Tests
# После запуска API, БД и ShopStub:
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/smoke.ps1
cd frontend
npm run build
```

`ExecutionPolicy Bypass` нужен только процессу запуска нашего локального теста на Windows с запрещёнными `.ps1`; он не меняет политику системы. Smoke-тест создаёт отдельные тестовые аккаунты и сборки в локальной БД. Не запускайте его на рабочей базе с пользовательскими данными. Сценарии API также доступны в `requests.http` через REST Client.

## Подключение магазина Семёна

Контракт описан в [docs/API.md](docs/API.md); JSON-схемы и примеры находятся в Swagger и `docs/openapi.json`. Укажите адрес магазина в `Shop__BaseUrl` и одинаковый случайный `Integration__ServiceKey` в обоих сервисах. Ключ передаётся только между backend через `X-Service-Key`, в React он отсутствует.

`ShopStub` — тестовый стенд с данными в памяти, которые сбрасываются при перезапуске; он не заменяет сервис Семёна и не должен публиковаться. Его учебные цены, остатки и операции нужны для проверки сборщика. При подключении настоящего магазина остановите стенд и смените URL. Для получения статуса корзины после сетевого сбоя сначала используйте «Обновить состояние»; клиент повторяет ключ незавершённого действия в текущей вкладке.

## Конфигурация и размещение

Для локальной разработки настройки находятся в `appsettings.Development.json` и Compose. Тестовые пароль БД и ключ явно обозначены как development-only. Для своего окружения создайте игнорируемый `src/PcAssembly.Api/appsettings.Local.json` либо используйте переменные:

```text
ConnectionStrings__AssemblyDb=Host=...;Database=...;Username=...;Password=...
Shop__BaseUrl=https://.../
Integration__ServiceKey=<случайная строка минимум 20 символов>
AllowedOrigins__0=https://<ваш-сайт>.netlify.app
Database__Initialize=true
```

`Database__Initialize=true` создаёт схему **новой** БД через EF Core EnsureCreated; оно не обновляет существующую схему. Для последующих изменений модели нужно добавлять миграции перед выкладкой. Схема начальной версии сохранена в `docs/database.sql`.

Dockerfile API: `docker build -f src/PcAssembly.Api/Dockerfile .`. В Amvera укажите production-переменные и порт 8080. Для Netlify: base directory `frontend`, build `npm run build`, publish `dist`, переменная `VITE_API_URL` — HTTPS-адрес API без завершающего `/`. API должен разрешать домен сайта в `AllowedOrigins`. Развёртывание в облаке в этой версии не выполнялось.

План-источник: `../План проекта/PLAN (1).md`. Исправленные диаграммы находятся в `docs/uml`. DOCX учебных отчётов остаются исходными: перед сдачей следует заменить в них схемы и пояснения по этим файлам.

Результаты и ограничения проверки: [docs/VERIFICATION.md](docs/VERIFICATION.md).
